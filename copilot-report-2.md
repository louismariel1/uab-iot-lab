1. Introduction

The objective of this first laboratory milestone was to establish and validate Bluetooth Low Energy (BLE) communication between a Nordic nRF52840-DK development board and an Edge device.

In the proposed IoT architecture, the Nordic board acts as the Device layer, responsible for generating sensor events and transmitting them through BLE. The Edge layer is represented by an Android smartphone running the nRF Connect application, which is used to discover, connect, and receive telemetry data from the device.

The main goal of this milestone was to demonstrate that telemetry data generated by the device can be successfully transported to an external BLE client.

3. BLE Communication Design

The BLE communication is based on the Generic Attribute Profile (GATT).

The following BLE mechanisms were implemented:

3.1 Advertising

BLE advertising is used to make the device discoverable by nearby clients.

The firmware advertises under the name:

SSP-POC


The Android device scans for nearby BLE devices and detects the board through its advertisements.

Purpose:

Device discovery
Connection establishment preparation
3.2 Connection

After discovery, the smartphone connects to the Nordic board.

The firmware logs successful connections:

CONNECTED count=1


Purpose:

Establish a communication session
Enable access to GATT services
3.3 GATT Services and Characteristics

The Nordic board exposes BLE services and characteristics through a GATT server.

The telemetry characteristic is used to transmit SSP events generated by the firmware.

Purpose:

Structured exchange of device telemetry
Standard BLE data access mechanism
3.4 Notifications

The project uses BLE Notifications to transmit telemetry data.

Notifications allow the peripheral to push data automatically to the connected client without requiring the Edge application to continuously poll the device.

Notification workflow:

Device generates event
        ↓
Serialize payload
        ↓
BLE Characteristic Update
        ↓
Notification Sent
        ↓
Edge Receives Data


After notifications are enabled, the device transmits one telemetry packet every 5 seconds.

Example log:

SSP event notifications: enabled

[NOTIFY] #1 len=17
[NOTIFY] rc=0


A return code of zero indicates a successful BLE transmission.

4. Telemetry Payload Design

A custom SSP protocol was implemented to transport telemetry information between the Device and the Edge.

4.1 Payload Size

The telemetry payload contains:

17 bytes

4.2 Payload Structure
Byte(s)	Field0	Protocol Version
1	Event Type
2	Status
3-6	Device ID
7-10	Sequence Number
11-14	Timestamp (ms)
15-16	Motion Value (mg)

All multi-byte fields use Little-Endian encoding.

4.3 Example Payload

Captured during testing:

01 01 00 01 50 53 53
01 00 00 00
B1 1C 02 00
08 07


Decoded value:

Version      = 1
Event Type   = 1
Status       = 0

Device ID    = 0x53535001

Sequence     = 1

Timestamp    = 138417 ms

Motion       = 1800 mg
