# PCB Flash and UART Smoke Test — nRF52840-DK

## 1\. Purpose

This smoke test verifies that the nRF52840-DK can be programmed using SEGGER J-Link and that the flashed Zephyr firmware boots and produces the expected UART output.

It validates the complete hardware and development path:

```
Windows 10
    ↓ USB
usbipd-win
    ↓ USB/IP
WSL2 / Ubuntu
    ↓
SEGGER J-Link
    ↓
nRF52840-DK
    ↓
Zephyr firmware
    ↓ UART
J-Link USB serial interface
    ↓
/dev/ttyACM0
    ↓
Python / pySerial listener
```

A successful test demonstrates that:

- Windows can share the J-Link USB device with WSL2.
- Ubuntu can access the J-Link and its serial interface.
- Zephyr can build firmware for the nRF52840-DK.
- `west flash` can program the board.
- The programmed firmware boots and emits the expected UART message.
- Python and pySerial can receive and validate that message.

This is a hardware and development-environment smoke test, not an SSP motion-detection or BLE integration test.

## 3\. Connect the J-Link to WSL2

Connect the nRF52840-DK to the Windows laptop using its USB connection.

Open Windows PowerShell:

```
usbipd list
```

Identify the J-Link device. Its USB vendor/product ID is:

```
1366:1025  SEGGER J-Link
```

For example:

```
BUSID  VID:PID    DEVICE
1-4    1366:1025  USB Serial Device (COM3), BULK interface, ...
```

The bus ID may change after reconnecting the board. Always use the current value reported by `usbipd list`.

Attach the device to WSL:

```
usbipd attach --wsl --busid 1-4
```

Replace `1-4` if the current bus ID differs.

In Ubuntu, verify USB access:

```
lsusb
```

Expected entry:

```
Bus 001 Device 002: ID 1366:1025 SEGGER J-Link
```

The device number and bus number may vary.

## 4\. Verify the UART interface

In Ubuntu/WSL:

```
ls -l /dev/ttyACM0
```

Expected:

```
crw-rw-rw- ... /dev/ttyACM0
```

Check the stable device identifier:

```
ls -l /dev/serial/by-id/
```

Expected entry:

```
usb-SEGGER_J-Link_000683321542-if00 -> ../../ttyACM0
```

The serial device name and identifier should be checked again whenever the board is reconnected.

Verify Python serial support inside the active environment:

```
python -c "import serial; print(serial.__version__)"
```

Expected:

```
3.5
```

The automated script currently invokes `python3`, rather than `python`. If the smoke test fails because the script uses a different interpreter, inspect `python3` and `python` separately before changing the script.

## 5\. Verify the firmware artifacts

Activate the environment and enter the Zephyr workspace:

```
pyenv activate zephyr-3.12
cd ~/zephyrproject
```

Check the firmware generated by the previous build:

```
ls -lh /tmp/ssp-hello-world/zephyr/zephyr.hex
ls -lh /tmp/ssp-hello-world/zephyr/zephyr.elf
```

Both files must exist.

The `.hex` file is the firmware image used for flashing. The `.elf` file contains the executable and debugging information.

If the files are missing, rebuild the application:

## 6\. Flash the board independently

From the Zephyr workspace, run:

```
cd ~/zephyrproject
west flash -d /tmp/ssp-hello-world -r jlink
```

The successful flashing output was:

```

-- west flash: using runner jlink

```

This confirms that the J-Link runner was selected and the firmware image was passed to the flashing tool.

A successful `west flash` validates programming, but **does not by itself prove that the expected UART message was received**. That requires the next step.

## 7\. Run the automated flash-and-UART test

The permanent smoke-test script is located at:

```
/home/louis/flash_hello_test.sh
```

Run it with the correct Python environment activated:

```
pyenv activate zephyr-3.12
~/flash_hello_test.sh
```

The script performs three stages:

1. Checks for the firmware image and serial device.
2. Starts a Python serial listener and flashes the board.
3. Waits for the expected UART message and reports PASS or FAIL.

Configuration in the current script:

```
BUILD_DIR="/tmp/ssp-hello-world"
SERIAL_DEV="/dev/ttyACM0"
BAUD=115200
TIMEOUT=15
EXPECTED="Hello World! nrf52840dk/nrf52840"
```

### Important: keep the expected message synchronized with the firmware

The SSP application's source currently prints:

```
SSP PoC Hello World! nRF52840
```

The first smoke-test run flashed and booted successfully, but the script still expected:

```
Hello World! nrf52840dk/nrf52840
```

Consequently, the first run reported FAIL even though the UART output was received correctly.

The script's `EXPECTED` value was subsequently corrected to match the actual firmware output.

To inspect the current configuration:

```
grep -nE 'BUILD_DIR|SERIAL_DEV|BAUD|TIMEOUT|EXPECTED' \
  ~/flash_hello_test.sh
```

The expected message must match the firmware's output exactly, including capitalization and punctuation.

### Timeout consideration

The listener uses a 15-second timeout and starts before flashing. If flashing or startup takes too long, the listener could time out before receiving the expected message.

If this becomes a recurring issue, increase the timeout or modify the script to manage the listening window more robustly. Do not interpret a timeout as proof of a hardware failure without checking the received UART output.

## 9\. Repeating the smoke test in future

Whenever the development environment has changed, the board has been reconnected, or the firmware toolchain is in doubt, run:

```
pyenv activate zephyr-3.12
cd ~/zephyrproject
ls -lh /tmp/ssp-hello-world/zephyr/zephyr.hex
ls -l /dev/ttyACM0
python -c "import serial; print(serial.__version__)"
~/flash_hello_test.sh
```

If the script fails, distinguish between:

- USB passthrough failure;
- missing serial device;
- incorrect Python environment;
- missing firmware image;
- J-Link flashing failure;
- UART timeout;
- expected-message mismatch.

The smoke test should remain separate from the SSP application tests so that hardware and toolchain problems can be isolated from application-level defects.
